# Paladin — AGI 时代的最小可执行架构范式

> **主线：会执行 → 会创作 → 会进化**

**Paladin 不是又一个 AI 框架。**

我们在构建 **"AGI 时代的最小可执行架构范式"**：

- **分工明确**（Commander / Dispatcher）—— 决策与执行分离，不混淆。
- **闭环生长**（生成 → 验证 → 修复 → 持久化）—— 每一次迭代都留下可用的产物。
- **树形演进**（版本 → 枝叶 → 文件）—— 让系统复杂度可管理，不熵增。

这套范式 **不依赖 AGI 是否到来**。它适用于今天所有的 AI 项目：
无论你调的是 GPT-4 还是 10 年后的 AGI，只要你的产物是代码、配置或决策，
这套树形架构都能承载它。

---

不是框架。不是库。是一套可执行的**架构规则**，让你在任何 AI 项目中都能回答三个问题：

| 问题 | 树的回答 |
|------|---------|
| 现在在哪？ | 树干→分枝→叶片，精确位置 |
| 要去哪？ | 北极星（树干）决定方向 |
| 下一步做什么？ | 当前分枝上未闭环的叶子 |

## 三大范式支柱

### 🛡️ 分工明确 — Commander / Dispatcher

决策与执行分离，不混淆。

| 层 | 命名 | 职责 | 类比 |
|----|------|------|------|
| 大脑 | Commander | 理解意图、拆解任务、规划步骤 | 将军 |
| 手脚 | Dispatcher | 路由、限流、容错、状态追踪 | 传令兵 |
| 护甲 | 三篱笆 (Cache/Router/Watch) | 缓存命中、模型路由、成本监控 | 盾牌 |

### 🔄 闭环生长 — 生成 → 验证 → 修复 → 持久化

每一次迭代都留下可用的产物。

```
用户说"提取标题"
  → Planner: 检测到工具 extract_title 不存在 → 触发合成
  → CodeGenerator: 生成 Python 函数代码
  → Validator: 沙箱执行测试用例（零依赖）
  → Loader: 动态注册到运行时
  → Executor: 执行工具，返回结果
  → 工具已持久化到 generated_tools/，下次直接可用
```

### 🌳 树形演进 — 版本 → 枝叶 → 文件

让系统复杂度可管理，不熵增。

```
🌳 Paladin
│
├── 🌱 会执行 (v0.1-v0.7)  ← 已闭环
│   └── 三篱笆 / 指挥官-调度官 / 配置化
│
├── 🌿 会创作 (v0.8)       ← 已闭环
│   └── 工具合成 / 热加载 / 持久化 / 自主缺位检测
│
└── 🌳 会进化 (v1.0)       ← 生长中
    ├── 🟢 沙箱验证
    ├── ⬜ 自动修复
    └── ⬜ 闭环集成
```

## 用户分层

Paladin 的定位是"最小可执行架构范式"，它既不是纯终端工具（如 curl），也不是企业级 SaaS 平台（如 Salesforce）。

### 🛡️ 开发者 / 技术负责人 — "会创作"的受益者

如果你是一名 Python 开发者，正在构建 AI 应用或内部工具，Paladin 是你的 **AI 开发助手**。

```bash
# 1. 零配置启动，先看靶场
pip install paladin-ai
paladin demo

# 2. 用自然语言描述需求，自动生成工具
paladin run "写一个工具，提取网页标题"
# 输出: ✅ 工具 'extract_title' 已生成并注册到 generated_tools/

# 3. 作为编排层嵌入项目
from paladin import Paladin
app = Paladin()
result = app.run("分析这份财报，生成摘要报告")
```

**核心价值**：把"写胶水代码"的时间从 1 小时压缩到 1 条命令。

### 🧑‍💼 产品 / 业务人员 — "会执行"的受益者

如果你不是开发者，但想验证一个 AI 想法是否可行，Paladin 是你的 **概念验证（PoC）加速器**。

1. 让开发者帮你跑 `paladin demo`——3 个场景展示多步推理、并行检索和条件分支。
2. 用自然语言描述业务逻辑，让开发者构建"测试工具"：
   > "我需要一个工具，输入客户 ID，输出最近 30 天的数据摘要。"
   
   开发者用 Paladin 生成这个工具，你就能在 **5 分钟内**获得一个可执行的脚本。

**核心价值**：把"提需求"到"能测试"的周期从 2 周缩短到 1 天。

### 🏢 企业 / 平台用户 — "会进化"的潜在受益者

如果你是一家公司的技术决策者，Paladin 代表一种 **架构范式**，而非单一工具。

- **内部 AI 治理框架**：用 Paladin 的"三篱笆"模式（缓存→路由→监控）作为 AI 调用的默认策略，确保成本可控、质量可回退。
- **跨项目复用**：`generated_tools/` 作为企业内部的"AI 工具库"，不同团队生成的能力自动沉淀为共享资产。
- **AI 能力"寄生"**：Paladin 最终形态可以以 sidecar 模式附在现有系统中，为老系统注入 AI 能力，不重构核心代码。

**核心价值**：把 AI 能力从"项目级依赖"提升为"企业级资产"。

## 反模式对照

| 堆砌模式 ❌ | 树形模式 ✅ |
|------------|------------|
| "先写着，后面再重构" | "先画树，再落第一片叶" |
| "这个功能以后可能用上" | "这个功能属于哪枝？不在树上就不写" |
| "改一个文件顺便修另一个" | "只动当前分枝的当前叶" |
| "版本推进不顺就回溯" | "分枝锁死后不回溯" |
| "新功能直接叠加上去" | "找到对应分枝，长新叶" |
